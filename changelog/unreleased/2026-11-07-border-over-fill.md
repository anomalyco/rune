- **Borders draw over the fill, as CSS paints a border over its background, and `El::border_sides` draws CSS per-side borders.** A border used to replace the fill under it, so a translucent ring on a filled box showed what was behind the element; it now draws over the fill, which runs under it to the outer edge, so a 0.5 pt `border_weak` ring on a code block measures 226 on white as Chromium draws it, not 229. Opaque borders look as before: on a rounded box the fill pulls in by half the border's width, as Chromium's bleed avoidance does, so no fill fringes the anti-aliased edge. Faded elements keep the same layering (an instance's `params.w` now carries the opacity its colours carry). Inset `box_shadow`s draw between the fill and the border and inside it (CSS's padding box), and a dashed border draws over them. `El::border_sides([top, right, bottom, left], c)` gives each side its own width, each snapped to device pixels like `border`, the ring narrowing round a corner, so a `border-bottom: 0.5px` port is the box's own last device row instead of a 0.5 pt rule after it that lands a row low at 1× and 1.25×. A hairline inset ring's square corner pixel now takes its exact area, as dark as Chromium draws it (it was up to 0.25 too faint at 1×). Apps with translucent borders on filled boxes see those rings take in the fill; to keep the old look, put the border on an unfilled child the same size. The CPU reference renderer (`rune-ref`) and its goldens follow, and the Windows DXBC is regenerated with the new `cargo run -p rune --example regenerate_dxbc`, which needs no test build. **macOS:** the precompiled `uber.metallib` and `uber_native.metallib` are stale until someone runs `scripts/precompile-metal-shaders.sh` on a Mac; until then the WGSL hash check fails closed and Macs compile the uber shader from WGSL at launch (correct pixels, a slower first surface), as they already did on `dev` since the last shader change.
