- **Windows: releasing a removed D3D12 device with work in flight no longer crashes with an access violation (`0xC0000005`).** After device removal D3D12 sets every fence to `UINT64_MAX` and rejects `Queue::Signal`, so `wgpu-core` freed in-flight command allocators, buffers, pipelines, and swap-chain resources immediately while the driver (reproduced on WARP) was still executing queued command lists. The vendored `wgpu-hal` (`vendor/wgpu-hal.patch`, `DrainTracker`) now records a `WriteBufferImmediate(MARKER_OUT)` marker at the end of each D3D12 command list into a 64 KiB readback buffer; `Queue::wait_for_idle` and `Device::wait_for_present_queue_idle` wait for all submitted markers to land (bounded by 250 ms stall / 1 s total timeouts for hardware drivers that discard queued work on reset), and `CommandEncoder::reset_all` skips `ID3D12CommandAllocator::Reset` on a removed device.
