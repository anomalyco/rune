- **Windows: releasing a removed D3D12 software-adapter (WARP) device with work in flight no longer crashes with an access violation (`0xC0000005`).** After device removal D3D12 sets every fence to `UINT64_MAX` and rejects `Queue::Signal`, while WARP's worker threads continue executing already-submitted command lists, so `wgpu-core` reset command allocators and freed in-flight resources under them. The vendored `wgpu-hal` (`vendor/wgpu-hal.patch`, `DrainTracker`) now records a `WriteBufferImmediate(MARKER_OUT)` marker per command list on software adapters (`DXGI_ADAPTER_FLAG_SOFTWARE`, caching `ID3D12GraphicsCommandList2` per pooled list) into a 64 KiB readback buffer and drains submitted markers in `Queue::wait_for_idle` and `Device::wait_for_present_queue_idle` (bounded by 250 ms stall / 1 s total timeouts). Hardware adapters and drivers without `WriteBufferImmediate` (`DIRECT`) run with no drain markers (zero steady-state marker cost); skipping `ExecuteCommandLists`, skipping `ID3D12CommandAllocator::Reset`, and sliced fence waits apply on every adapter.
